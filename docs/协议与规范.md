# 评测协议与代码规范

---

## 一、四条统一

| # | 统一的 | 说明 |
|---|---|---|
| 1 | **最终接口 = 每像素一个簇标签** | 无论算法内部在超像素 / 样本 / 视图上工作，最后都要归约到像素标签 |
| 2 | **评价函数** | 一律由 `common/metrics.py` 计算，**不采信任何算法自报的数字** |
| 3 | **评分像素** | 一律只评 `gt > 0` 的像素（同一批） |
| 4 | **划分与种子** | 同一份划分、同一组种子 |

**唯一不统一的**：预处理与超参各自调优 —— 这是**有意为之**，因为不同算法为不同数据结构设计，硬套统一预处理反而制造不公平。

---

## 二、四个指标的口径

| 指标 | 定义 | 易错点 |
|---|---|---|
| **ACC** | 匈牙利最优标签置换后的准确率 | 必须先置换；不置换会把 ACC 打到随机水平 |
| **NMI** | 互信息，**算术平均**归一化 `2·MI/(H_pred+H_true)` | 有实现的变量名叫 `NMI_sqrt` 是误导，实现其实是算术平均 |
| **ARI** | 调整兰德指数（Hubert–Arabie） | — |
| **Purity** | 每簇取占比最大的真值类，累加后除以 N | **不是**置换后的 ACC——允许多个簇映射到同一个真值类 |

实现见 `common/metrics.py`。

## 三、诚实读出协议

### 问题

所有以 k-means 作为最终读出步骤的方法，最后一步都是"把表示硬分成 K 类"，而这一步需要随机初始化。

**同一份表示、同一批数据，只换随机初始化，ACC 能差 10 个百分点以上。**

### 很多论文的做法

> 跑多次 k-means，**用真值挑 ACC 最高的那一次**上报。

实测这种 oracle 选择能虚高 **8.6 个百分点**。

### 本平台的强制规定

```
sklearn KMeans(n_clusters=K, n_init=10, random_state=固定种子)
按 inertia（簇内平方和）选初始化，固定取最后一次迭代的结果
```

### 因此

**本平台所有数字都低于各方法论文中的报出值。** 这不是"跑坏了"，而是论文数字包含了 oracle 选择的虚高。所有方法一视同仁地受此约束，所以排名仍然公平。

## 四、BLAS 线程数必须固定

### 现象

同一份数据、同一个种子、同一个算法，**只改线程数**：

| BLAS 线程 | ACC |
|---|---|
| 24 | 0.6483 |
| **4** | **0.6014** |
| 1 | 0.6605 |

**差 5.9 个点。** 而超参网格里大多数配置之间的差距还不到 5 个点。

### 原因

计算机的浮点加法**不满足结合律**：

```
数学上：  (a + b) + c  =  a + (b + c)     永远相等
计算机里：(a + b) + c  ≠  a + (b + c)     末位可能不同
```

多核并行 = 计算顺序被打乱 → 末位不同 → 在 10 轮迭代里**不断放大** → 最终聚类标签不同。

### 本平台的做法

`common/threads.py` 在 `import common` 时**强制**把线程数钉死为 **4**，用 `threadpoolctl` 在运行时生效（不靠环境变量，因为环境变量只在库首次加载前有效）。

**不要改这个数字。** 改了所有历史结果都没法和新的比。

### 自检

```bash
python scripts/verify_threads.py
```

应显示"本包固定线程数 4 / 实际生效 4"，并打印一个可跨机器比对的校验和。

### 残留风险

即使线程数相同，**不同代 CPU 仍可能有末位差异**——OpenBLAS 会按 CPU 型号选不同指令集（AVX2 / AVX512）。这属正常，**不影响结论量级**。

每条结果记录里必须带着"这个数字是在什么条件下跑出来的"：

```json

  "dataset": "Trento",
  "method": "example_kmeans",
  "ACC": 0.5947,
  "blas_threads": 4,      ← 协议指纹
  "seed": 0,              ← 协议指纹
  "partition": "none",    ← 协议指纹
  "timestamp": "..."
}
```

## 六、像素顺序：统一用 F 序（列优先）

平台所有展平操作都是 **Fortran 序（列优先）**：

```python
ds.flatten_view(v, "F")     # (H, W, B) → (N, B)
ds.flatten_gt("F")          # (H, W)    → (N,)
```

**如果你的算法用的是 C 序（行优先，numpy 默认）**，传回标签前必须置换：

```python
labels_platform = labels_c.reshape(H, W).reshape(-1, order="F")
```

**不置换的话标签会整体错位，指标会掉到随机水平**（K 类时约 1/K）。

## 七、接口契约

每个算法文件对外只暴露一个函数：

```python
run_<算法名>(ds, seed=0, **kwargs) -> (labels, detail)

  labels : (N,) int32   每像素一个簇标签
  detail : dict         元信息（耗时 / 超参 / 通信量……）
```

自动发现规则：扫 `methods/*.py`，跳过 `_` 开头的文件，其余文件里定义了
`run_<文件名>(...)` 的就当作一个算法。

## 八、划分范式（做联邦方法时用）

| 范式 | 客户端持有什么 | 适用 |
|---|---|---|
| **视图划分**（垂直联邦） | 每个客户端一个**模态**，全部像素 | 不同传感器由不同机构持有——遥感的真实场景 |
| **区域划分**（水平联邦） | 每个客户端一块**地理区域**，全部视图 | 按地理切块 |

统一接口见 `common/partition.py`

### 联邦方法的额外要求

1. **`detail` 里必须带通信量**：`{"comm_bytes": 总字节数}`
   —— 这样所有联邦方法用同一口径，才比得了"谁的联邦化代价小"
2. **强烈建议验证无损性**：如果算法本身可无损切分，联邦版和集中版的**中间结果应当逐元素相同**。
   参考：某算法联邦化后 10 轮迭代 `max|ΔH| = 0`，即精度零损失，代价全在通信量上。
